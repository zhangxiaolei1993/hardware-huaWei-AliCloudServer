### AD-1 表情标签集是否严格等于 8 类白名单？

- **服务器 A 的白名单**：`neutral, happiness, surprise, sadness, anger, disgust, fear, contempt`
- **要核实**：
  1. 设备端表情分类模型输出的**全部可能标签**是什么？
  2. 是否存在额外值，如 `unknown` / `none` / `no_face` / `unrecognized` / 空字符串？
  3. 是否做过标签名映射（如 `happy` → `happiness`）？映射表在哪？
- **为什么重要**：A 端 `POST /emotion/sessions/{sid}/data` 对 `expression` 做枚举校验，**任何不在白名单的值会导致整批 422**，进而整段数据丢失。
- **请提供**：标签定义位置（模型输出类 / 枚举常量 / 映射表）与全部取值。
- **影响设计**：§12 U-1 白名单、§2.11.7
- **核实结论（已由设备端 §11 AD-1 核实）**：标签集**严格 8 类**，唯一来源为 `LABELS` 常量，与服务端逐字一致；**无人脸不写记录**；无映射/别名；不会因标签集触发 422。

### AD-2 `relative_seconds` 的原点 `t0` 精确取自哪个时刻？

- **已知**：`relative_seconds = time.time() - t0`，且 `t0` 取在 CLAIM（轮询到活跃会话）时刻。
- **要核实**：
  1. `t0` 的赋值语句在哪个文件哪一行？
  2. `t0` 取的是「收到 `active-session` 响应」、「首次检测到人脸」、还是「会话 `session_start`」？
  3. 如果中途断线重连，`t0` 是否重置？（这会导致同一会话内时间轴跳变）
  4. 会话结束（FINISH）后 `t0` 是否保留？
- **为什么重要**：A 端的锚点 `anchor_utc_at` 必须与设备的 `t0` 是同一时刻，否则 `relative_seconds` 无法对齐到统一时间轴。
- **请提供**：`t0` 赋值代码 + 断线重连处理逻辑。
- **影响设计**：§8.2 锚点机制
- **核实结论（已由设备端 §10 核实，部分）**：设备端只有 `relative_seconds` 与会话级本地墙钟 `session_start/end`（**无时区**），**没有单条记录的绝对时间**。因此 `t0` 只在本会话内相对有效，不能直接作为 UTC 锚点依据。

### AD-3 设备端能否在不重启采集的情况下读取单调时钟？

- **要核实**：
  1. 设备端运行的 Python 版本？
  2. 是否已在任何地方使用 `time.monotonic()` / `time.perf_counter()`？
  3. 改为单调时钟是否会影响现有帧循环（是否有依赖墙钟的逻辑）？
- **为什么重要**：`time.time()` 会被 NTP 跳变影响，必须改单调时钟；但改造范围取决于现有代码对墙钟的依赖程度。
- **请提供**：Python 版本 + 当前所有 `time.time()` 使用点清单。
- **影响设计**：决策 D1、§8.3
- **核实结论（已由设备端 §10 核实）**：设备时钟**未对时**，当前无单调时钟时间源可用于跨请求时间对齐。结论：禁止用 `session_start + relative_seconds` 反推时间并标为 `device`，只能标 `estimated` 或 `missing`。

### AD-4 能否读取硬件序列号？

- **要核实**：
  1. 设备是否能读取唯一硬件标识（如 `/proc/device-tree/serial-number`、`/sys/class/.../serial`、网卡 MAC）？
  2. 如果读不到，是否有其他稳定唯一标识（如 eMMC CID）？
  3. 该标识是否会在重刷系统后改变？
- **为什么重要**：当前 `device_id` 手写死 `atlas_001`，多台设备会撞 ID，且换机会继承旧身份。
- **请提供**：可用的序列号来源 + 实际取值样例（可脱敏）。
- **影响设计**：决策 D3、§2.11.2
- **核实结论（已由设备端 §11 AD-4 核实，无法确认）**：程序**完全不读硬件标识**；`device_id` 为**静态配置**；注册体**无 SN 字段**；全仓库无 `serial`/MAC/CID 读取。
  → 设备身份绑定**无法仅靠端侧落地**；换机沿用旧配置会**继承旧身份与 token**。P0 只能做「配置槽位 + 注册快照 + 变更告警」，硬件身份（`hardware_serial`）推迟 P2（详见总文档 §22 D3）。

### AD-5 上传失败的重试逻辑是否区分错误类型？

- **已知**：重试 5 次带退避，422/409 不重试。
- **要核实**：
  1. 重试的**完整错误分类表**（哪些 HTTP 码重试、哪些不重试）？
  2. 重试期间进程重启，重试计数是否丢失？
  3. 重试耗尽后，数据是丢弃、留在本地、还是标记失败？
  4. 4xx 不重试时，数据是否还留在本地 spool？
- **为什么重要**：决定补传是否会堆积「死信」，以及服务器 A 能否在 `late_upload_deadline` 内收到数据。
- **请提供**：重试逻辑代码 + 错误分类表 + 耗尽后的处理。
- **影响设计**：§16.2、P0-11
- **核实结论（已由设备端 §10 核实）**：设备端**不重试**，只保留本地底稿。因此服务器 A 任何 4xx/422 都等于**该次采集数据永久丢失**（除非人工补传）。这直接支撑 D1 的「不拒绝、只标记」策略。

### AD-6 FINISH 后落盘的 JSON 是否在上传成功后删除？

- **要核实**：
  1. 落盘文件路径与命名规则？
