## 0. 一句话总结

v1.3 的架构方向没有错，但有 8 处「同一件事被写了两个阶段」的自相矛盾。v1.4 只做一件事：**给每个能力确定唯一阶段**，并把由此产生的接口语义、迁移步骤、验收标准一次性对齐。

| # | v1.3 的矛盾 | v1.4 的结论 |
| --- | --- | --- |
| 1 | 设备端单调时钟既是 P0-10，又是 P1-4/P1-12 | **P1**；P0 设备端零改动 |
| 2 | P0 要求设备 spool，但断网补传是 P1 | **整块归 P1-17**；P0 只验服务端幂等 |
| 3 | `X-Api-Key` 在 §17.2/D12 是 P0，在 P1-7/AC-15 是 P1 | **P0（P0-17 / AC-15）** |
| 4 | baseline 被写成「首次执行 upgrade」 | **存量库只能 `stamp <baseline_revision>`**，前置逐表比对 |
| 5 | `questionnaire_code` 被写成 B 正式编码 | **客户端 `scale_id` 文本化**，稳定性待 B 确认（X-6） |
| 6 | 派生时间与记录 `quality` 混用 | **派生不落库、不改 `quality`**，单独记 `derived_time` |
| 7 | D5「不引入 `result_version`」被误读为所有结果表 | **仅 `emotion_results`**；快照表保留 `result_version` |
| 8 | 加密范围表述含混（鉴权/脱敏被当成加密） | **P0 无 TLS/证书/传输加密/加密存储/校时**；鉴权与 HMAC 脱敏各归其位 |

## 1. 修订项 R1：设备端时间改造阶段修正

**问题**：v1.3 §19.2 的 P0-10 要求「设备端 `relative_seconds` 改单调时钟、上传顶层增加 `stream_id`」，而 §19.3 的 P1-4 与 P1-12 又把同一改造列为 P1。§2.11.4 的结论 2 也写着「设备端**必须**……（P0-10）」。

**修改**

| 位置 | 修改内容 |
| --- | --- |
| 文件头 | 版本升 v1.4，列出 8 项修复 |
| §2.11.4 结论 2 | 「必须（P0-10）」→「**建议**，归 **P1-4 / P1-12**；P0 保持 `relative_seconds = time.time() - t0`，不要求设备改单调时钟」 |
| §8.1 能力分层表 | `event_timestamp` 行的 P0 列改为「**不落库**，导出按需派生」；`monotonic_ms` 行保持「不要求」 |
| §8.7 版本台阶 T1 | 时间点由「P0/P1」统一为 **P1-12**（P0 仍为 T0） |
| §19.2 P0-10 | **整行划掉**，标注「已移出 P0（v1.4）→ P1-4 / P1-12；P0 `stream_id` 由服务器补全（P0-14）」 |
| §19.3 P1-4 | 显式纳入「`relative_seconds` 由 `time.time()` 改为 `time.monotonic()` 基准」 |
| §19.6 Gantt | 删除 `P0-10 时间戳与单调时钟` 行；设备端段改为「**P0 零改动**」，新增 `P1-4/12` 行 |
| §19.6 依赖图 / 顺序原则 | 改为「设备:【P0 零改动】→（P1）时间改造 → spool」；新增原则 5 |
| 附录 D | D.2 增「阶段纪律（设备端）」校验项 |

**结论**：P0 设备端**零改动**——`relative_seconds = time.time() - t0` 保留、原三字段上传保留、`stream_id` 由服务器按接口路径自动补全（P0-14，标 `quality=legacy` 与 `stream_defaulted` flag）。`device_timestamp` / `frame_index` 仍按原计划在 P1/P2。

## 2. 修订项 R2：设备端 spool 队列阶段修正

**问题**：v1.3 的 P0-11 要求设备实现「持久化 spool 队列 + 稳定幂等键」，理由是要让 AC-05b 通过；但同一份文档又把断网补传整体列为 P1。§3.3 还写着「需设备端 spool 队列（P0）」。这构成「P0 必须实现 spool，但断网补传属于 P1」的直接矛盾。

**事实前提**（AD-8 已核实）：设备端当前**没有任何持久化队列**——采集期间仅内存，FINISH 时落盘一份 JSON，失败只打日志、不自动重发，进程崩溃即丢。

**修改**

| 位置 | 修改内容 |
| --- | --- |
| §3.3 独立运行保证 | spool 标注改为「**P1-17**；P0 不要求设备补传，只验收服务端幂等 AC-05a」 |
| §6.5 时间线用例表 | 「断网补传（设备）」行加「**P1-17 才实现**」 |
| §15.7 | 「真正补传必须依赖 **P1-17** 的 spool 队列（P0 不要求设备补传）」 |
| §16.1 三端职责 | 设备端「目标」列标注 **P1-17**，「P0 设备端零改动，不要求任何队列」 |
| §16.2 | 标题加「**P1-17；P0 不实施**」，新增阶段口径块，明确整节归 P1 |
| §19.2 P0-11 | **整行划掉** → P1-17；P0 只验收服务端批次幂等（AC-04 / AC-05a） |
| §19.3 | 新增 **P1-17 设备端持久化 spool 与补传**（含稳定幂等键、启动扫描、重启续传） |
| §19.6 | 删除 `P0-11` 行；新增 `P1-17 spool队列与稳定幂等键` 行；依赖图改为 P1 |
| §21.3 | **AC-05 拆为 AC-05a（P0）/ AC-05b（P1）**，表格与说明块同步 |
| §21.4 | 「补传成功率」指标明确 P0 只验 AC-05a |
| §23.1 AD-8 行 | 引用由 `P0-11 / AC-05` 改为 `P1-17 / AC-05b` |

**结论**：P0 上传可靠性**只由服务端保证**——批次幂等键 `UNIQUE(session_id, source, client_request_id)`、重复上传返回 `duplicate:true`、不重复入库。断网/崩溃后补齐是 **P1-17** 的交付内容。

**问题**：v1.3 中 §17.2 三阶段表与 §22 D12 把 `X-Api-Key` 查询鉴权列入 P0，但 §19.3 的 P1-7 与 §21.3 的 AC-15 又把它列为 P1。

**修改**

| 位置 | 修改内容 |
| --- | --- |
| §12.5 | 「阶段归属」引用块：基础 `X-Api-Key` 属 P0（P0-17 / AC-15）；P1 只做增强；**并声明明文 HTTP 下 Key 仍可能被窃听，基础鉴权≠传输加密** |
| §17.2 | 强制项第 2 条展开为「P0-17 / AC-15」；加「P1-7 不再重复加鉴权」与「HMAC 不属加密」说明 |
| §19.1 | P0 目标补「**基础查询鉴权**」；服务器配置列补 `QUERY_API_KEY` |
| §19.2 | 新增 **P0-17 基础查询鉴权（`X-Api-Key`）**：设备列表 / 会话查询 / 结果查询 / 科研导出统一校验；`401`；`/health` 与设备上报（走 token）不受影响 |

| 附录 D | D12 行「P0 期间」列写明「日志脱敏 + 基础查询鉴权（P0-17）+ 身份保护」 |

## 4. 修订项 R4：Alembic 生产迁移流程补充

**问题**：v1.3 §20.3 把 baseline 写成「在隔离副本上执行 upgrade head，确认无差异」，落地时极易被理解为「生产也执行 upgrade baseline」。但生产库**已有 6 张表且在跑业务**，baseline 是「补记录」而非「建表」。

**修改**

| 位置 | 修改内容 |
| --- | --- |
| §20.3 落地步骤 | 重写为 9 步，明确第 6 步生产**不是 upgrade，而是按 §20.3.1 对齐** |
| **§20.3.1（新增）** | 「生产库 baseline 对齐」：备份+`integrity_check` → 导出 `prod.schema` → 副本 `upgrade head` 导出 `baseline.schema` → **逐表逐列比对**（表名/列名/类型/可空/默认值/主键/唯一约束/索引）→ **仅完全匹配时** `alembic stamp <baseline_revision>` → 再逐个执行 P0 后续 revision（每个先 `--sql` 审阅） |
| §20.3.1 禁止事项 | ① 禁 `alembic stamp head`（会跳过 M1–M7）② 禁把 baseline 当建表迁移在生产执行 ③ 禁未备份/未在副本演练就 upgrade ④ 禁结构不匹配时「先 stamp 再说」⑤ 禁一次 upgrade 到 head 不逐条审阅 |
| §20.3.1 处置 | 不匹配必须**停止迁移**并分析差异（手工 `ensure_index.py` 补索引、历史未记录 ALTER、ORM 滞后），baseline 描述**现状**不描述目标态 |
| §20.5 检查清单 | 新增 2 项卡点：已导出 `.schema` 并逐表比对通过；生产使用 `stamp <baseline_revision>` 且未用 `stamp head` |
| §19.7 影响面 | 新增「存量库纳入 Alembic」行（需副本演练，回滚难度中） |

**结论**：本轮**未连接、未操作任何数据库**，只补流程与卡点。迁移执行仍属 P0 实施动作，需另行走变更审批。

## 5. 修订项 R5：结果同步字段确认（`questionnaire_code` / `result_version`）

**问题**：v1.3 §14.2 写「`questionnaire_code` 取 `get_one_scale.data.id` 字符串化」，容易被读成「服务器 B 在结果里返回量表编码」。实际是**客户端把 `scale_id` 文本化后上报**，B 的结果体没有该字段。同时 §14.4 示例用了 `"3"`，与实测 `22` 不一致。

**修改**

| 位置 | 修改内容 |
| --- | --- |
| §11.2 数据字典 | 改为「一期取**客户端 `scale_id` 文本化**（实测 `22`），不是 B 正式返回编码；稳定性待确认（X-6）」 |
| §11.2 `result_version` | 补充「**由客户端维护**（B 不返回版本号，也没有 `result_id`）」 |
| §14.1 事实表 | 新增两行：`questionnaire_code` 真实来源；`result_version` 归属 |
| §14.2 A 字段表 | `questionnaire_code` 行重写，明确「不是权威编码」+ 待 B 确认 + 确认前不得称永久稳定 |
| §14.4 | 整数规范化段落改为「客户端取到的 `scale_id` 为 int」；新增**幂等键风险提示**（B 侧 ID 变更会导致重复入库）；示例 `"3"` → `"22"` |
| §22 D2 | 新增「量表编码来源」行 |
| §23.3 | 新增 **X-6**：需 B 确认 `scale_id` ①是否跨版本稳定 ②是否全局唯一 ③改版后是否变化；**P0 集成前置确认项** |
| §21.3 | 新增 **AC-36**：`"022"`/`"22.0"`/`"PHQ-9"` → 422；且验收材料不得声称编码永久稳定 |

**结论**：`questionnaire_code` 按「客户端维护的量表标识」使用，**未确认前不作稳定性承诺**；B 无 `result_id`，`result_version` 是客户端版本字段。

## 6. 修订项 R6：时间质量定义统一

**问题**：v1.3 §8.1 写「`event_timestamp` 导出时派生并强制标 `estimated`」，与 §8.5 的记录级 `quality` 混在一起，容易被实现成「能派生时间就把 `quality` 升为 `estimated`」。同时 §8.2 没有明确「服务器会话创建时刻 ≠ 设备 CLAIM 时刻」。

**修改**

| 位置 | 修改内容 |
| --- | --- |
| §8.1 | `event_timestamp` 行改「**不落库**，导出派生，标 `estimated` 且**不得回写、不得提升 `quality`**」；新增三行对照表（派生时间 / `quality` / `quality_info.derived_time`）+ 三条硬规则 |
| §8.2 | 新增「**P0 同步精度声明**」：两个时间锚点不同，相差轮询周期 + RTT（2–5s）；P0 只能宣称「同会话内一致性对齐」，**不得宣称精确跨模态同步**；任何精度表述必须带 `anchor_uncertainty_ms`（P0 默认 5000） |
| §8.5 | `quality_info` 示例增加 `derived_time`（含 `source`/`method`/`anchor_uncertainty_ms`/`estimated_event_timestamp`/`note`）；写入规则新增第 6 条「派生时间不得回写质量」并给出禁止反例 |
| §21.3 | 新增 **AC-35**：对 `missing`/`legacy` 数据导出，派生时间存在但库内 `quality`/`flags` 未被修改 |
| §21.4 | 新增指标「派生时间标注率 100% 带 `anchor_uncertainty_ms`」 |
| 附录 D | D.2 新增「时间质量」校验项 |

**结论**：派生时间只出现在导出物与 `quality_info.derived_time`；记录 `quality` 一次性写入、不再变化；P0 的时间承诺是「同一会话内相对时间可比」，不是「绝对时间精确」。

**修改**

| 位置 | 修改内容 |
| --- | --- |
| §22 D5 标题 | 「P0 不引入版本」→「P0 **仅对 `emotion_results` 不引入版本**」 |
| §22 D5 决定 1 | 追加适用范围说明：本条**仅针对 `emotion_results`**；`external_result_snapshots.result_version` **保留**，按 §14.4 参与 `UNIQUE(session_id, questionnaire_code, result_version)`；**不存在「所有结果表禁用 `result_version`」的规则** |
| 附录 D D5 行 | 规则描述同步加限定语 |
| 附录 D D.2 | 新增「版本字段」校验项 |

**结论**：`emotion_results` 始终单行、无版本列；结果快照有版本列且参与唯一约束。两者不冲突。

## 8. 修订项 R8：加密范围明确

**问题**：v1.3 把「查询鉴权」「HMAC 脱敏」与「TLS/加密」混在同一段叙述里，容易让读者以为「P0 已经做了加密改造」。

**修改**

| 位置 | 修改内容 |
| --- | --- |
| §17.2 | 明确 P0 强制项清单；新增「HMAC `subject_ref` 是不可逆脱敏关联标识，**不是加密存储、不是传输加密**，与 TLS/证书无关，不能抵扣 S1/S2 风险」 |
| §17.3 | 身份脱敏行补同样的限定语 |
| §22 D12 | 新增「**加密范围的准确表述**」块：P0 **不实施** HTTPS/TLS、证书、传输加密、静态加密存储、设备校时；P0 **实施** 日志脱敏、基础查询鉴权、设备身份管理；`subject_ref` 不是加密；不得用于宣称 P0 已做加密改造 |
| 附录 D D12 行 | 补「基础查询鉴权属访问控制、不等于传输加密；`subject_ref` 为脱敏标识、不属加密」 |

**结论**：P0 **没有**任何传输/存储加密；保留的是日志脱敏、基础查询鉴权、设备身份管理。安全加固整体在 **P1-16**，需求未删除、只是阶段后移。
