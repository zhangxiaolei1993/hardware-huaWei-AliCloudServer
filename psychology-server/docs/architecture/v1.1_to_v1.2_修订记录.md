4. **不覆盖历史**：v1.1 文档原样保留；本记录与 v1.2 的附录 C.5 仅追加说明。
5. **全文语义一致**：每项修订都同步检查正文、决策表、数据字典、迁移、API 示例与验收用例，不能只改一处。

## 2. 逐项修订明细

### R1　N1 与 S1 的一对多关系及唯一约束（最高优先级）

| 项 | 内容 |
| --- | --- |
| **修改章节** | §6.2、§6.5、**§6.5.1（新增）**、§6.8（时序图 + C5 + **C7 新增**）、§11.1、§11.2、§11.4 M4、§12.3 S-1、§13.4、§14.2.1、§14.4、§19 P0-5、§21 AC-02/**AC-32~AC-34**、§22 D5、附录 C.5、附录 D |
| **原有问题** | v1.1 一方面在 §6.2/§11.2/§12.3 写 `UNIQUE(source_system, external_session_id)`，另一方面 §6.8 C5 又声明「同一 N1 可对应多个 S1」。二者互斥：一旦建唯一约束，「重新采集 / 重新连接设备」这类正常业务会被数据库直接拒绝。同时幂等语义被绑在 N1 上，导致「换新采集」被误判为重复请求；结果快照也可能被错误挂到同 N1 的另一次采集上。 |
| **修改内容** | ① `sessions.external_session_id` 改为**普通索引、不唯一**；② 创建幂等改为 `UNIQUE(source_system, client_request_id)`（`client_request_id` 允许 NULL，多条 NULL 不冲突）；③ 新增 §6.5.1 明确同一 N1 的三种情形：**重试创建**（同 `client_request_id` → 200 `created:false`）、**重新采集**（新 `client_request_id` → 201 新 S1，响应附 `related_session_ids`）、**重复上传**（同批次键 → 200 `duplicate:true`）；④ 结果快照幂等键改为以 S1 为作用域的 `res:{session_id}:{questionnaire_code}:v{n}`，`external_result_snapshots.session_id` NOT NULL；⑤ 明确 Server A 不得替换/改写 Server B 生成的 N1；⑥ 结果与 S1 不匹配 → 422 `RESULT_SESSION_MISMATCH`；⑦ M4 不再包含任何「sessions 外部 ID 唯一约束」变更。 |
| **修改原因** | 让「一对多」在数据库层真正成立；把「一次创建请求」与「一次业务测评」解耦；让结果必须落到具体某一次设备采集，而不是靠 N1 猜测。 |
| **影响数据库** | 是。新增列 `client_request_id`、唯一约束 `(source_system, client_request_id)`、普通索引 `(external_session_id)`；**删除** `UNIQUE(source_system, external_session_id)` 的设计。 |
| **影响 API** | 是。`POST /sessions` 新增必填/推荐字段 `client_request_id`；响应新增 `related_session_ids`；新增错误码 `RESULT_SESSION_MISMATCH`、`IDEMPOTENCY_KEY_MALFORMED`、`IDEMPOTENCY_CONFLICT`。 |
| **影响 P0 开发** | 是。P0-2（Session 管理）、P0-5（上传幂等）、P0-8（结果摘要）、P0-13（Flutter 改造）均需按新规则实现与验收。 |

### R3　Timeline 时间上界规则统一

| 项 | 内容 |
| --- | --- |
| **修改章节** | **§8.4（整节重写）**、§8.5、§12.4 U-1、§22 D10、§21 AC-09/AC-10、附录 C.5、附录 D |
| **原有问题** | v1.1 在 §8.4 使用 `session_elapsed + 300s` 且超界 **422**，在 §8.5/§12.4 使用 `+600s` 且超界 **只标记**。同一条数据在两章得到相反结论；同时没有说明批量上传时 `session_elapsed` 如何计算，也没有区分「合法性校验 / 质量标记 / 研究筛选」三层。 |
| **修改内容** | ① 唯一上界：`relative_seconds <= session_elapsed + 600`；② `session_elapsed` 计算依据：会话已结束用 `ended_at − started_at`，未结束用 `server_received_at − started_at`；③ 三层分离：L1 合法性（负值 `< -5.0` → 422 `INVALID_TIMELINE`；重复时间戳 → 422 `DUPLICATE_TIMESTAMP`；明显未来时间 → 422 `CLOCK_SKEW_TOO_LARGE`）、L2 质量标记（上界超出 → 200 + `out_of_range`；`[-5,0)` → `pre_anchor`；墙钟倒退 → `clock_jump`）、L3 研究筛选（导出/分析侧按 flag 过滤，服务端不做）；④ 明确「上界超限只标记、绝不 422」，杜绝「一边拒绝一边写 `out_of_range`」；⑤ 明确设备会话提前结束、延迟上传、设备时间异常三种场景的处理。 |
| **修改原因** | 设备整会话单批上传且失败不重试，任何 4xx 等于该段数据永久丢失；上界本身只是「可疑」而非「不可能」，应归质量标记而非合法性拒绝。 |
| **影响数据库** | 否（仅校验与 `quality_info.flags` 内容）。 |
| **影响 API** | 是。422 与 200+flag 的边界被固定；新增 `INVALID_TIMELINE`、`DUPLICATE_TIMESTAMP`、`CLOCK_SKEW_TOO_LARGE`。 |
| **影响 P0 开发** | 是。上传接口校验、质量标记、AC-09/AC-10、导出说明均需按新规则。 |

| 项 | 内容 |
| --- | --- |
