# P1 后续安全加固及设备能力升级清单（v1.4 对齐版）

| 项目 | 内容 |
| --- | --- |
| 依据文档 | 《AI 心探探多模态数据采集平台总体架构设计说明书 **v1.4**》§17.5 / §19.3 / §21.3 / 附录 D |
| 制定日期 | 2026-11-17 |
| 适用范围 | P0 业务联调完成之后的近期工作（P1），含**安全加固专项 P1-16** 与**设备能力升级** |
| 排期 | **P1-16 时间另行确认**；设备能力项（P1-4/P1-12/P1-17）建议紧随 P0 稳定后启动 |
| 本轮性质 | 只出清单，不改代码、不改设备固件、不动服务器配置 |

> **总原则**：P1 的所有安全项在 P0 **都没有被取消**，只是**阶段后移**。P0 使用明文 HTTP 是已明示的阶段性安排，不得据此认为安全需求已关闭。

## 1. 两类 P1 工作

| 类别 | 内容 | 阻塞关系 |
| --- | --- | --- |
| **A. 安全加固专项（P1-16）** | 域名与证书、Nginx/443、双端 HTTPS、设备校时、证书校验、Token 保护、HTTP 入口关闭与安全验收 | 前置 = 「P0 业务联调稳定」；**不阻塞任何 P0 阶段** |
| **B. 设备能力升级（P1-4 / P1-12 / P1-17）** | 单调时钟、显式 `stream_id`、`device_timestamp`、持久化 spool 与断网补传 | 前置 = A 端 P0 字段与 `upload_batches` 已上线 |

> 两类**互相独立**：可以先做 B 后做 A，也可以并行；但 **P1-17 的补传能力必须晚于 P0-5 的批次表**，否则幂等键无处落。

### 2.4 过渡期与倒计时规则

- **当前不启动倒计时**：尚未实施 HTTPS，90 天过渡期不成立；
- **起算日 = 安全专项正式上线日**（不是现在，也不是批准日）；
- 关闭条件：在役设备全部升级 **或** 到达截止日，二者取先到；
- 过渡期内旧端仅可访问白名单路径，且必须留审计。

## 3. B 类：设备能力升级

### 3.1 P1-4 设备时间基准改造

| 项 | 内容 |
| --- | --- |
| 目标 | `relative_seconds` 由 `time.time() - t0` 改为 `time.monotonic()` 基准；`session_start/end` 带时区 |
| 现状 | 墙钟、无时区（AD-9）；P0 保持不变 |
| 影响 | 消除墙钟跳变与 NTP 校正导致的倒退 |
| 验收 | 时钟跳变场景下 `relative_seconds` 单调不倒退 |

### 3.2 P1-12 显式流与设备时间字段

| 项 | 内容 |
| --- | --- |
| 目标 | 上报 `stream_id`、`device_timestamp`（带时区）、`monotonic_ms`、`X-Protocol-Version` |
| 现状 | 均无（AD-11）；P0 由服务器补默认流 |
| 影响 | `quality` 可从 `legacy`/`missing` 升到 `estimated`；仍不得直接为 `device`（墙钟未校验） |
| 验收 | 服务端收到显式 `stream_id` 后不再补默认流；质量分布看板可见 |

### 3.3 P1-17 持久化 spool 与断网补传（原 P0-11）

| 项 | 内容 |
| --- | --- |
| 目标 | 本地追加写队列 + 独立补传线程 + 重启续传 + 稳定幂等键 `{session_id}:{stream_id}:{batch_seq}` |
| 现状 | **无任何持久化队列**（AD-8）：仅内存 + FINISH 留底，崩溃即丢、重启不补传 |
| 前置 | **P1-12 的显式 `stream_id`**（否则退化为默认流单流）；**P0-5 的 `upload_batches`** 已上线 |
| 验收 | **AC-05b**：断网 1 小时或采集中重启，未 ack 批次全部补齐、不重复、顺序正确 |
| 禁止 | 用 `output/` 留底 JSON 充当补传队列（该文件不自动重扫） |

### 3.4 P1-3 设备自建会话与门控

| 项 | 内容 |
| --- | --- |
| 目标 | 无活跃会话时自建（独立模式闭环）；CLAIM 前 `session_type` 门控（G2） |
| 现状 | 设备不读 `session_type`（AD-7），任何类型会话都会采集 |
| 验收 | 非 `emotion` 会话不被误采 |

### 3.5 P1-14 设备 token 自动轮换

| 项 | 内容 |
| --- | --- |
| 目标 | 注册/心跳响应携带 token 版本并原子落盘；`device_identity` 变更上报 |
| 前置 | P0-15 已提供 `rotate-token` / `revoke` / `reinstate` |
| 验收 | 轮换后旧 token 立即失效、设备无中断 |

## 5. 顺序与依赖

```text
P0 业务联调稳定
   ├─► P1-6 查询组（可与设备升级并行）
   ├─► 设备: P1-4 单调时钟 ─► P1-12 显式 stream_id ─► P1-17 spool（AC-05b）
   ├─► P1-7 权限分级与 token 哈希（M9）
   └─► 安全专项 P1-16：PRE-1…PRE-7 ─► SS-01…SS-20 ─► SS-A1…SS-A7 ─► 启动过渡倒计时 ─► P1-15 关闭 8000
```

**不可违反**：

1. P1-17 必须晚于 P0-5（`upload_batches`）；
2. P1-15（关闭 8000）必须晚于设备升级完成或过渡截止日；
3. P1-16 不得倒排进 P0；
4. 安全专项上线前不得对外宣称「已做安全加固」。

## 6. 与 P0 的关系（防止误读）

| 问题 | 回答 |
| --- | --- |
| P0 的明文 HTTP 是否等于放弃安全？ | **否**。是阶段后移；日志脱敏、基础查询鉴权、设备身份管理在 P0 已强制 |
| P0 是否已经加密？ | **完全没有**。无 TLS、无证书、无传输加密、无加密存储 |
| HMAC `subject_ref` 算加密吗？ | **不算**。是不可逆脱敏关联标识，不提供机密性 |
| P0 能否宣称跨模态精确同步？ | **不能**。锚点不同，须带 `anchor_uncertainty_ms` |
| 安全需求是否被删除？ | **没有**。SS-01…SS-24、SS-A1…SS-A7 全部保留 |
