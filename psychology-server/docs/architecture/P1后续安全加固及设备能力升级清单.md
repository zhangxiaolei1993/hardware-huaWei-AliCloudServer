## 0. 结论摘要（先看这 7 条）

1. **导出能力已经写了一半**：仓库里 `app/api/exports.py` + `services/export_service.py` + `schemas/export.py` 完整存在且有 5 个测试，但**生产服务器上没有这三个文件，`main.py` 也没有挂载它们**——生产 20 条路由中没有任何 export/manifest 路径。之前的生产 ImportError 是「先部署了引用方、后补被引用模块」的部署顺序问题，不是代码缺陷。因此**不需要重写，复用并补齐即可**；但 P1 第一步先做脚本，不急着上线接口。
2. **导出目前只覆盖表情原始序列**：现有接口只导出 `emotion_records`（单会话、同步生成、CSV/JSON），`modalities` 参数被接收但未生效；**不导出 timeline 事件、不导出结果、不导出外部测评快照**，也没有批量与打包。
3. **三列「未来字段」其实早已存在**：`emotion_records.device_timestamp / monotonic_ms / frame_index` 是 P0 M6 已建的列，只是客户端从未填写（生产 24,956 行**填充率均为 0**）。用户提示词中「不增加这三列」应改为「**沿用已有列、不再新增**」。
4. **表情记录质量全部是 `legacy`**：生产 24,956 行 `quality` 100% 为 `legacy`，`stream_id` 100% 为服务器补的 `facial_expression`，`quality_info`/`protocol_version` 填充率 34%。导出必须显式带质量列，不能把 `legacy` 当默认值隐藏。
5. **真正的「版本化」在外部结果快照，不在表情结果**：`external_result_snapshots` 已有 `result_version` + `supersedes_snapshot_id` + 唯一约束 `(session_id, questionnaire_code, result_version)`，幂等键 `res:{S1}:{code}:v{n}` 属于它；而 `emotion_results` 是 **`UNIQUE(session_id)` 单行覆盖**，每次重算 UPDATE 同一行，**没有任何历史版本**。任务四的缺口在表情结果，不在量表结果。
6. **多模态挂同一 S1 的机制已经具备**：`session_devices`（一会话多设备、primary/auxiliary）+ `devices.capabilities` + `session_type` 白名单已含 `physiological` + `upload_batches` + 统一的 `relative_seconds` 锚点，足以让心率/ECG 设备作为 auxiliary 挂到同一 S1。**P1 不需要为此建表或改接口**，只需要把规范写死。
7. **设备端没有任何持久化队列**：采集期间 timeline 只在内存，FINISH 时写一份 `output/cloud_upload_*.json` 留底，上传失败只做最多 5 次进程内指数退避，**不重扫、不续传、重启即丢**。任务三必须新增 spool，属于设备端文件级新增，服务端零改动。

## 3. 任务二（P1-B）：多模态统一接入规范（克制版）

### 3.1 现状（已核实）

- `sessions.session_type` 白名单已含 `physiological`、`multimodal`、`speech`、`custom`；当前 78 个会话全部是 `emotion`。
- `devices.capabilities` 是 JSON 数组（现为 `["emotion"]`），注册时由设备自报。
- `session_devices` 支持一会话多设备（`primary` / `auxiliary`），`UNIQUE(session_id, device_id)`，会话结束仍保持 `bound`（迟到上传依赖此状态）。
- `timeline_events.stream_id`、`emotion_records.stream_id` 已存在；`data_streams` 表**尚未建**（原 P1-11）。
- `emotion_records` 的列是表情专用（`expression` / `confidence` NOT NULL），**不能**用来存心率或 ECG。
- 现有跨模态关联键：`session_id`（S1）+ `device_id` + `relative_seconds` + 锚点。

### 3.2 P1-B1 数据类型标识（只定取值，不建表）

| `modality` | 中文 | 形态 | 典型单位 | 采样 |
| --- | --- | --- | --- | --- |
| `facial_expression` | 表情识别 | 离散序列（帧级） | 类别 + 置信度 | 事件驱动 |
| `speech_audio` | 语音/语言交互 | 离散事件 + 可选音频文件 | 毫秒 / 字节 | 事件驱动 |
| `heart_rate` | 心率 | 连续时间序列 | bpm | 1–10 Hz |
| `ecg` | 心电波形 | 连续波形 | mV | 250–1000 Hz |
| `blood_panel` | 血液检测 | 离散检测结果 | 项目相关（g/L、mmol/L…） | 单次 |
| `questionnaire` | 量表过程 | 离散事件 | 无 | 事件驱动 |

- 数据来源沿用现有 `source`（`device` / `app` / `server`），**不新增来源枚举**。
- 新增模态的判定规则：能在 `session_devices` 绑定 → 用同一 S1；不能绑定 → 才考虑独立会话。**P1 不建任何模态表**。

### 3.3 P1-B2 时间与单位规范

1. 时间：一律 UTC ISO8601（毫秒 + `Z`）；会话内相对时间统一用 `relative_seconds`（同一 `anchor_utc_at` 原点）；跨设备精度只能声明为「同会话内对齐」，必须带 `anchor_uncertainty_ms`。
2. 单位：入库存**规范单位**，单位随值走（`unit` 列或 JSON 键），不允许裸数字；转换在接入端完成，服务端不改写。
3. 采样：连续流必须声明 `sample_rate_hz` 与 `channel_count`；离散结果必须声明 `measured_at` 与 `method`（设备/试剂/版本）。
4. 缺失：`null` 表示未采集；`0` 不得表示缺失；质量标记沿用 `quality` 四值语义。

### 3.4 P1-B3 两类存储形态建议（仅建议，不落地）

| 形态 | 适用 | 建议结构 | 理由 |
| --- | --- | --- | --- |
| **连续时间序列** | 心率、ECG、PPG、EEG | **元数据行 + 分段/文件**：一行描述流（stream_id、modality、unit、采样率、起止、文件 URI、sha256、字节数），样点落在分段文件 | 数据库不被波形撑爆；备份/导出按文件走；可校验完整性 |
| **离散检测结果** | 血液检测、单次生理测量 | 一次检测一组行：`code`、`value`、`unit`、`ref_range`、`measured_at`、`method` | 与量表维度同构，便于表格导出与统计 |

### 3.5 ECG 取舍分析（只给结论，不实现）

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 波形 BLOB 入库 | 单库自包含、事务简单 | 单条 30 s×500 Hz 即数万点；库体积与备份时间线性膨胀；分页/抽样查询困难 | **不推荐** |
| B. 元数据表 + 分段文件（推荐） | 库轻、文件可校验、导出天然按文件打包；分段便于断点补传 | 需管理文件生命周期与一致性 | **推荐**；分段建议 10–60 s 或 ≤1 MB；文件与元数据同 sha256 |
| C. 对象存储 + 索引 | 易扩展、适合多中心 | 引入外部依赖与网络失败面 | P2 再评估 |

触发条件建议：单段样点 > 10,000 或字节 > 1 MB → 走文件；否则可随离散结果存 JSON（仍不建表）。

### 3.6 最小改动与验收

- 表/字段/接口：**P1 全部为零**。仅新增本文档的取值表；若开发时需要，最多新增一个 `app/core/modalities.py` 常量（纯字典，不建表、不预埋空字段）。
- 对 P0 兼容：不改 `session_type` 白名单、不改设备注册、不改任何路由。
- 验收：任意新模态都能回答四个问题——`modality` 是什么、时间用哪个原点、单位是什么、数据落在「流+文件」还是「离散行」；且不需要改 P0 表结构。
- 风险：规范过早细化会束缚实现 → 本文只定「标识/时间/单位/形态」，不定字段名与表名；真正接入时再出迁移。

## 4. 任务三（P1-C）：数据可靠性与自动补传

### 4.1 现状（已核实，设备端 `app-trae`）

- 采集期间 `timeline` 仅在内存；FINISH 时写 `output/cloud_upload_<时间>.json` 留底，然后调用 `POST /emotion/sessions/{sid}/data`。
- 重试：`CloudClient` 对网络错误与 408/429/5xx 做最多 `upload_max_retries=5` 次指数退避（上限 16 s），422 立即失败不重试。
- **无队列文件、无启动扫描、无重启续传**；留底 JSON 不会自动重发。
- 服务端已有批次幂等 `UNIQUE(session_id, client_request_id)`，重复提交返回 `duplicate:true`；迟到上传窗口默认 24 h（`late_upload_deadline`）。
- 生产 `upload_batches` 仅 4 行（P0-5 之后的批次），说明历史绝大多数上传没有批次记录，但幂等已由结果侧兜底。

### 4.2 最小改动（设备端新增，服务端零改动）

**P1-C1 新增 `app-trae/cloud/spool.py`（约 150 行）**

- 目录：`data/spool/<session_id>/<client_request_id>.json`；写入用「临时文件 + `os.replace`」原子落盘。
- 内容：`session_id`、`client_request_id`（沿用 P1-17 的稳定键 `{session_id}:{stream_id}:{batch_seq}`）、`payload`（session_meta + timeline）、`created_at`、`attempts`、`last_error`。
- 状态：文件存在 = 待上传；服务端返回 2xx（含 `duplicate:true`）= 完成 → 删除文件；超过 `late_upload_deadline`（24 h）或超过磁盘配额 → 移到 `data/spool/_expired/` 并告警日志，**不静默删除**。

**P1-C2 采集脚本挂钩（`run_cloud_assessment.py`）**

- FINISH 后：先写 spool，再立即尝试上传；上传成功删文件，失败保留。
- 进程启动时：启动一个补传线程扫描 spool（按 `created_at` 升序），逐条重放；同一 `client_request_id` 复用，保证幂等。
- 补传线程与采集线程解耦，失败退避上限 60 s，不阻塞采集。
- 留底 `output/cloud_upload_*.json` 保留不动（人工核对用），不再承担补传职责。

### 4.3 对 P0 的兼容保证

- 服务端不加字段、不加接口、不改幂等键；补传用的就是现有上传接口。
- 设备端仅在 `app-trae` 新增文件与启动钩子；不改上传契约、不改采集主循环。
- 24 h 窗口是服务端既有约束，spool 只服从，不试图绕过。

### 4.4 验收标准

1. 断网 1 小时后恢复：spool 中的评测全部自动上传成功，且同一 `client_request_id` 在服务端只有一条结果（`duplicate` 生效）。
2. 上传过程中 `kill -9` 设备进程并重启：spool 文件仍在，重启后补传成功。
3. 超过 24 h 的待传项：进入 `_expired` 并产生明确日志，不阻塞其它项。
4. 正常联网路径：行为与现在一致（上传成功后 spool 清空），`output/` 留底仍生成。
5. 磁盘配额（建议 500 MB）触发时拒绝新入队并告警，不损坏已有文件。

### 4.5 风险

| 风险 | 处置 |
| --- | --- |
| 设备磁盘小、波形未来会更大 | 本阶段只存 JSON timeline；配额 + 过期隔离；波形文件另属 P2 |
| 补传线程与服务端 24 h 窗口冲突 | 入队时记录截止时间，过期即隔离并提示 |
| 重复上传造成结果重算 | 幂等键是批次级，重复请求直接返回 `duplicate`，不重算 |
| 采集进程与补传线程竞争 | 独立线程 + 文件锁（按 session 目录）；上传接口本身无状态 |

## 5. 任务四（P1-D）：原始数据与分析结果分离

### 5.2 最小改动（新增只追加表，不动 P0 表）

### 5.4 验收标准

1. 同一会话上传两次（不同批次）：`emotion_results` 仍 1 行且为最新值；`emotion_result_versions` 2 行，`version` 1→2，`source_record_count` 递增，`source_sha256` 与原始记录一致。

3. 导出物能通过 `source_sha256` 回溯到对应原始记录集合。
4. 历史 45 个会话不因迁移产生错误；`versions` 为空时导出明确标注。
5. P0 全量测试通过（重点：上传、结果查询、多批次、迟到上传）。

### 5.5 风险

| 风险 | 处置 |
| --- | --- |
| 每次上传都写版本，行数增长 | 每次上传本就重算，1 会话版本数 = 批次数；可接受；必要时导出按需过滤 |

| 误把版本表当权威结果 | 文档与导出均标明：`emotion_results` 是当前值，版本表是历史 |
